# Perspective Ads 要件・実装方針

## 1. 作品の狙い

街中の広告は、見る人に情報を送り続ける一方通行になりやすい。そこで、声を出したり画面に触れたりせず、立ち位置を少し変えると商品広告の見どころが変わる体験を試作する。

今回確かめるのは、視点に反応する写真広告が、商品への関心や内容の想起につながるかどうかである。クーポンは広告を見るきっかけと次の行動を補助するが、商品より目立たせない。

主な設置先は、駅などの公共空間にある縦型デジタルサイネージとする。画面比率は縦長の9:16を基本にし、通行中に商品写真とコピーを見つけやすく、特典を得た後はスマートフォンへ移れる設計にする。PCモニターは実装確認用であり、主要な利用環境とはしない。

## 2. 体験仕様

1. 正面では、ステーキの全体写真と商品コピーを広告として表示する。
2. 顔が画面左へ動くと、同じ構図の艶を増したステーキ写真へ切り替わり、焼き目に寄る。湯気や炎の合成エフェクトには頼らない。
3. 顔が正面のまま画面へ近づくと、顔の画面占有サイズを前進の目安として、全体写真から断面写真へ段階的に切り替える。写真全体をパン・拡大せず、皿の位置と大きさを保つ。
4. 特典情報とQRコードは商品写真の左脇に置き、通常は透明にしておく。写真を左右へ動かして無理に隙間を作らず、少し左へ覗くと余白に現れる。現れたときは重なる店名ロゴを退かし、QRコードの直上に短い読み取り案内を見せる。大きな白い券面や独立した販促パネルにはしない。
5. QRコードは約2.5cm相当の左移動、または断面が十分に現れる前進量から表示を始める。どちらの動きでも最後まで進めば全体が表示される。読み取ると、スマートフォン向けの特典受取画面を開く。PCのクリップボード操作をサイネージ上の主要導線にはしない。
6. 特典情報は広告コピーの下へ別パネルとして追加しない。サイネージ上では写真の奥に小さなQRと短い案内だけを置き、割引額とコードは表示しない。読み取り後のスマートフォン画面で特典内容を確認し、受取ボタンを押すと利用確認用の一回限りのデモコードを発行する。特典表示のための注視時間は設けない。
7. 店側のデモ画面でコードを入力すると利用済みにし、同じコードの再利用を拒否する。QRページ表示・特典受取・利用確認の件数を表示する。
8. 最初に戻す操作で広告と特典の状態をリセットする。

縦型画面では写真を上段、広告コピーを下段に置く。特典情報とQRコードは写真領域の裏側に置き、商品写真の輪郭で隠れる配置とする。券面全体がせり出す表現は避け、QRコードだけに読み取りに必要な大きさと余白を確保する。横画面は開発・比較用に引き続き対応する。

左右の切り替えには進入・復帰距離の差を設け、顔位置の小さな揺れで表示が往復しないようにする。顔追跡が使えない場合も、画面ドラッグとデバッグ表示中の矢印キーで体験を確認できる。

広告の挙動を確かめるため、画面上の検証パネルでカメラ接続・顔検出・前進量・断面・QRの表示進捗を確認できるようにする。手動検証を有効にするとカメラ入力を一時停止し、左右移動と前進量をスライダーで再現できる。必要な場合に限り、利用者が画面とカメラの録画を開始し、広告画面とカメラ映像を同時に記録する。映像は音声を含めず別ファイルで保存し、ローカルへのダウンロード後にバックエンドの一時ファイルを削除する。

## 3. 現行実装

### フロントエンド

- Reactで広告コピー、カメラ状態、特典状態を管理する。
- 切り抜いたステーキ写真は左右移動でパンさせず、固定構図のまま見どころを切り替える。縦画面では商品をやや右へ寄せ、左の余白にQRコードを置く。
- 焼き目は同じ構図の艶を増した素材へ切り替える。正面から近づく動きでは、初期位置で測った顔サイズとの比率から前進量を推定し、全体写真と断面写真の不透明度を連続的に変える。写真の位置と大きさは固定する。
- 顔の左右位置を正規化し、DeadzoneとOne Euro Filterを通して見どころの選択へ反映する。前進はFace Mesh全体の正規化境界の幅と高さから得た面積相当値を初期値と比較する。実距離や視線を計測するものではない。
- QRは約2.5cm相当の左移動、または前進量60%から表示を始め、左移動約8.5cm相当または前進量90%で全体を表示する。QRの遷移先はスマートフォン向け特典受取画面で、受取操作後に個別の一回限りデモコードを発行する。
- 受取キーごとに同じコードを返し、再読み込みや通信再試行で重複発行しない。店側のデモ画面では初回だけ利用確認を記録し、QRページ表示・発行・利用確認の件数を集計する。
- カメラ未接続時は横ドラッグで左右、縦ドラッグで前進を再現する。デバッグ表示中は矢印キーでも各方向を確認できる。
- `VITE_COUPON_URL`が設定されている場合はその公開URLへ遷移させ、未設定時は同じ配信先の`coupon.html`を使う。
- 画面をドラッグして視点を動かせる。`D`でデバッグ表示、表示中は矢印キーと`Space`で入力を確認できる。`R`で最初に戻り、`F`で全画面表示を切り替える。
- 「検証」パネルでカメラ接続・顔検出・現在位置・前進量・断面表示・QR表示進捗を確認できる。顔を一時的に見失った場合は900ミリ秒位置を保持してから初期位置へ戻す。
- 手動検証を有効にすると顔追跡入力を一時停止し、左右移動と前進量をスライダーで再現できる。手動検証を終了すると初期位置へ戻り、カメラ入力へ復帰する。
- 「画面とカメラの録画を開始」は利用者が画面共有先を選んだ後に両方の録画を開始する。画面はWebM、OpenCVが取得しているカメラ映像はAVIとして同じ記録名で別々にダウンロードする。カメラ映像は停止後のダウンロードまでバックエンド内に一時保存し、ダウンロード後に削除する。音声は記録しない。タブやカメラ接続が録画中に切れた場合はカメラの一時ファイルを破棄する。

### バックエンド

- OpenCVとMediaPipe Face Meshで顔の左右位置と顔サイズを取得し、FastAPIとSocket.IO経由でフロントエンドへ送る。
- カメラ映像はローカルのPythonバックエンドで処理し、通常はブラウザーへ顔位置などの状態情報だけを送る。録画中に限り、利用者が開始操作をしたカメラ映像をAVIに一時記録し、利用者へのダウンロード後に削除する。
- カメラの起動・利用不可・顔未検出の状態をフロントエンドへ通知する。
- `PERSPECTIVE_CAMERA_ENABLED=0`を設定すると、画面を配信したままカメラ処理だけを停止できる。未設定時は従来どおりカメラを起動する。

## 4. 素材と特典

- ステーキの全体・艶違い・断面の写真と湯気素材は、体験の流れを確かめるために生成したコンセプト素材である。焼き目の状態変化は別画像への切り替えであり、実際の加熱や物理的な湯気を再現するものではない。実在チェーンの商品や実際の提供内容を再現したものではない。
- QRページで発行するコードは受取キーに結び付いた一回限りのデモコードで、店側デモ画面で利用済みにできる。実際の割引、注文、決済、店舗システムとは連携しない。割引内容とコードはサイネージには表示せず、QRを読み取った後のスマートフォン画面だけに表示する。受取記録と件数はローカルSQLiteへ保存し、利用者の個人情報は取得しない。
- ローカルでスマートフォンから試す場合は、`127.0.0.1`ではなく、同じネットワークからアクセスできるPCのアドレスでサイネージ画面を開く。実運用ではスマートフォンから到達できる公開URLを設定する。
- 実際の広告へ展開する際は、広告主から利用許諾を得た商品写真、コピー、特典条件へ差し替える。

## 5. 検証仮説

視点に反応する広告が、静止広告より自発的な視点移動を生み、商品内容の想起を損なわずに特典へつなげられるかを確かめる。

少人数の比較では、静止広告と「商品詳細の変化後に特典を出す広告」を見せ、以下を記録する。

- 自発的に左右へ動いた人の割合
- 商品広告の前にいた時間
- 商品名、焼き目、火入れなどの想起
- クーポンを認識した割合と商品コピーへの注意

滞在時間だけでは、関心と戸惑いを区別できない。再訪や日次利用への効果も、この試作だけでは主張しない。

## 6. 制約と後回しにするもの

- 表示中のものは写真とコピーの切り替えであり、写真に写っていない商品部分を3D復元するものではない。
- 顔位置から得られる左右移動と顔サイズ比はカメラに対する相対値であり、顔の向きや姿勢にも影響される。実空間の正確な頭部位置、前進距離、視線そのものではない。
- 複数人追跡、視線推定、広告配信管理、店舗で使える実クーポンの発行、日次リテンション分析は対象外。コード発行・一度限りの利用確認はデモ内で検証する。
- 商品カテゴリやジェスチャーを増やす前に、ステーキ広告で視点移動が商品理解とクーポン導線を両立できるかを確かめる。
